# Engineering Meta-Principles

Before changing code, identify the owning runtime, trust domain, and business capability from the accepted architecture and existing module layout; put the change there instead of creating a generic `shared`, `common`, `utils`, or speculative abstraction. Keep applications, routes, command handlers, and composition roots thin; keep domain logic host-independent; expose the smallest public API; and cross module boundaries only through declared package exports, contracts, or ports—never through deep imports or another module's repository. Follow established English domain terminology and language conventions: use `kebab-case` for TypeScript files/directories, `camelCase` for values, `PascalCase` for types/components, `fooSchema` for Zod schemas, and idiomatic Rust naming. Do not edit generated files; change their source and regenerate them.

While implementing, validate every untrusted boundary from `unknown`, reject unknown or invalid wire data, fail closed, keep secrets out of ordinary TypeScript, logs, errors, and non-secret persistence, and never bypass runtime authorization, tenant isolation, or dependency boundaries for convenience. Add proportionate tests beside the owning module, including negative tests for security and protocol boundaries. Before finishing, run the relevant checks (use root `pnpm check` for a complete repository change), inspect the repository for every affected term and assumption, and update code, contracts, configuration, generated outputs, examples, and current-state documentation together. Explain invariants and rationale in comments rather than restating code; document narrow temporary exceptions with their reason and removal condition, and require an ADR for architectural exceptions.
