# 产品对谈与决策记录

本记录收集产品负责人于 2026-11-18 提供的事实和需要进一步确认的使用场景。
待答项不是已接受的限制，也不自动授权扩大现有运行时能力。范围和架构决策在信息充分后形成，
需要修改 ADR 时更新对应主题的最终规则；不从营销材料或开发中的缺口反推产品目标。
本轮已确认决策分别归入 [ADR-0027](adr/0027-multi-platform-domain-providers-and-marketplaces.md)、[ADR-0023](adr/0023-business-backup-and-recovery.md) 与 [ADR-0020](adr/0020-commercial-entitlement-and-local-access.md)。

## 已确认

- 开发者本人也是域名投资人，当前约管理 **300 个域名**。
- 资产分布：**22.cn、ename.com、aliyun.com、GoDaddy、Spaceship、Cloudflare**。
- 优先解决：统一域名管理、交易平台自动批量上下架，以及自动处理平台所有权验证。
- 交易平台优先级：**Afternic → Atom → Spaceship SellerHub → Sedo → 易名 → 阿里云 → 22.cn**。
  API 由工程侧核查，见 [API 与接入核查](PROVIDER_API_REVIEW.md)；该排序不是对账户已获准的声明。
- 产品负责人进一步确认：目前未找到官方 API 支持的能力缺口，后续全部走自研私有 API 开发；
  社区代码仅作参考，不再等待社区成品或更多官方搜索。不能把缺少官方 API 当作永久人工限制。已接受接入边界见 [ADR-0027](adr/0027-multi-platform-domain-providers-and-marketplaces.md)。
- 原有八平台保留，新增 Sedo、易名、阿里云、22.cn，共十二个平台。22.cn、易名和阿里云
  首发同时支持资产归集与批量上下架；该范围已由产品负责人明确确认。
- 非资金批量操作：**整批预览确认一次，再自动完成各平台操作与验证**。计划应明确列出跨平台
  所有权验证所需的 DNS 修改；执行不得超出用户批准的目标与变更，资金操作仍独立确认。
- 恢复必须覆盖两条旅程：**换机云恢复**和**独立业务备份**。现有仅限同一安装的 GDBK v1
  不能单独满足目标；应实现可恢复性，而非把不可用状态当作终点。
- 独立备份必须在**原电脑丢失且 GoodDealer 云不可用**时，凭用户保管的恢复材料，在新电脑
  恢复、查看和导出业务数据。恢复数据不依赖 Cloud；Provider 外部操作仍需有效授权，
  不能由备份恢复旧授权或凭据。恢复材料的具体形式和保管体验由实现设计确定。
- 商业与营销策略应能随市场调整。现阶段先把支持运营变化的基础设施搭好，不预先认定某种
  价格或商业方案永久成立。当前已接受的商业规则在新决策前继续生效。
- 按功能和所有权拆分架构，以支持扩展和维护；数据库原子事务、授权和秘密隔离不因拆分失效。
- **Windows 与 macOS 首发均完整支持**平台连接、批量操作和恢复。不能将 Windows 当前缺失的
  原生实现视为产品范围排除；两端分别完成实现与验证。
- 应用运行时后台继续执行；休眠或退出时暂停，重开后先对账再续作。不要求关机期间执行。
  对已发出但未确认的操作先查询平台实际状态，避免将不确定结果直接作为失败重试。
- 整机丢失时恢复**最近一次备份**即可，不新增固定数据丢失窗口或自动备份调度要求。
  独立备份主要服务换机，由用户手动选择本地保存位置；GoodDealer 不替用户决定同步盘、NAS
  或外置盘策略。平台可查询的上下架状态可在重新授权后扫描对齐；用户自定义且平台无法重建的
  业务数据以备份内容为准。云恢复以最后成功同步的副本为准，不能承诺恢复未同步数据。
- 营销不指导技术实现。开发阶段的目标功能需要被实现，不能仅因其尚未交付就删减目标。

## 商业基础设施设计方向

商业策略由 Cloud Licensing 拥有。调整价格、优惠、销售地区或 Provider 时，应能追溯规则版本，
保持已购订单、付款与授权期限的历史事实；客户端仍只消费服务器验证过的权益。运营配置需要
严格校验、授权、审计和回滚，而不把价格或优惠判断分散到 Desktop、营销或支付 webhook 中。
这是后续设计的约束，不表示上述运营界面已经实现，也不在此提前决定新价格或新增支付渠道。
