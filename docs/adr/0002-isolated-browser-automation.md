# ADR-0002：采用隔离且由用户授权的浏览器自动化

状态：Accepted  
日期：2026-07-30

## 背景

部分域名平台没有公开 API、API 不覆盖所有操作，或者要求用户先在网页中完成登录、2FA、CAPTCHA 和所有权确认。只支持 API 和 CSV 会导致大量流程仍需离开 GoodDealer 手工完成。

同时，直接让远程平台页面运行在拥有高权限 Tauri Command 的应用 WebView 中，会使恶意页面、XSS 或错误导航有机会触及本地资产和密钥。

## 决策

GoodDealer 支持用户授权的浏览器自动化，但采用双 WebView 信任模型：

- Local App WebView 只加载本地应用代码并拥有受限业务 IPC。
- Remote Browser WebView 加载平台页面、保存本地会话并执行自动化，但不拥有高权限 Tauri IPC。
- 用户自行完成密码、2FA 和 CAPTCHA。
- 软件只在用户对具体操作计划授权后接管后续页面操作。
- 页面状态不明确、目标元素不唯一或页面版本不兼容时停止执行并交还用户。
- 页面脚本回传只视为 Observation；写操作需重新加载页面、独立 API/报告或用户确认后才完成。
- Windows WebView2 与 macOS WKWebView 必须在 Phase 0 通过 Profile、脚本回调、弹窗/OAuth 和下载拦截闸门。

自动化规则使用签名、版本化、受限 Recipe，不允许更新服务下发任意系统代码。

## 结果

优点：

- 可以覆盖无 API 或 API 不完整的平台。
- 登录凭证和 Cookie 保留在用户本机。
- 用户可以在同一客户端完成登录、授权和后续操作。
- 远程网页不能直接访问数据库、Keychain 和文件系统。

代价：

- Windows WebView2 与 macOS WKWebView 的行为差异需要测试。
- 页面改版会造成 Recipe 失效，需要快速签名更新和回滚机制。
- 浏览器自动化可靠性低于正式 API，必须提供用户接管和人工降级。
- 平台使用条款和自动化限制需要逐个平台评估。

## 不采用的方案

### 完全禁止内嵌网页

不采用。会使 API Key 获取、网页验证和无 API 平台流程割裂。

### 让远程页面运行在主应用 WebView

不采用。远程内容不应与高权限本地 UI 共享 IPC 权限和会话环境。

### 自动代填密码、2FA 或绕过 CAPTCHA

不采用。认证环节必须由用户本人完成。

### 任意 JavaScript/系统脚本插件

不采用。自动化更新使用受限 Recipe，不能访问任意本地资源或执行系统代码。
