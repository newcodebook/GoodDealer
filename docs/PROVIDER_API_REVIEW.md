# 域名平台 API 与接入路径核查

核查日期：2026-11-18。本轮继续核对七个优先交易平台的官方文档、公开帮助及社区仓库源码。
只读取公开资料，没有使用客户凭据、执行平台业务请求、运行社区代码、申请权限或联系平台。
文档合同已确认不等于账号获准、接口实测成功或 GoodDealer 已交付；未找到公开合同也不等于不存在 API。
搜索摘要和搜索引擎生成的回答不作为接口证据。

产品负责人进一步决定：已确认官方支持的能力走官方 API；目前未找到官方支持的能力缺口，
后续全部走自研私有 API 开发。社区代码仅作参考，不再等待社区成品或追加官方搜索才启动工作包。
接入边界见 [ADR-0027](adr/0027-multi-platform-domain-providers-and-marketplaces.md)。本轮重点为资产归集、卖家上下架和所有权验证，
并非十二平台所有注册商、获取、DNS 能力的完整资格审查。

Linux 真实账户库存观察到两个响应行为。未投影的 `maxLeasePeriod` 可以为 `0`，且已返回声明总数的终页仍可能带 `next`。库存读取支持该零值；其他租售期仍限 `2–60`。终页链接仍经过固定 HTTPS 来源、路径及有界查询校验，读取按已确认的总数结束。真实账户首次归集 188 项，重开复读 188 项、无重复新增。

### Atom

2026-11-20 读取当前官方 OpenAPI 1.0.0。库存固定 `GET https://www.atom.com/api/marketplace/domains`，使用 `api_token`、整数 `user_id`、`page`、`limit`，响应文档为 JSON 数组。匿名真实请求返回 HTTP 200 和 `text/html`，响应体为 `{"message":"API Token and UserId are required"}`。Native 明确识别这种认证错误，正常库存须为 JSON 数组。账户库存读取使用有界逐页扫描、拒绝重复 Listing ID 和域名，直到空页才提交。官方合同没有总数或快照标识，真实账号验收需与卖家页面核对计数和翻页。价格币种和状态终态仍待取证。

`add-domain`、`remove-domain`、`verify-dns` 的官方文档使用 **GET**；它们仍是有副作用的操作，
不能进入通用只读缓存、预取、探活或自动重试路径。Token 在 query 内，完整 URL 不得进入日志、错误和遥测。
官方 `GET /domains` 支持 `type=standard`，可在认证账户内核对下架前的类型及资源身份。`remove-domain` 只支持 Standard。筛选结果缺席仍需精确账户读取对账。`add-domain` 的 Premium 类型会扣除一枚 coin，并提交平台审核。[筛选](https://apidocs.atom.com/api-reference/seller_apis/domains) [下架](https://apidocs.atom.com/api-reference/seller_apis/remove_domain) [上架](https://apidocs.atom.com/api-reference/seller_apis/add_domain)
Native 已组合无筛选和 `type=standard` 的双完整读取。仅当两个清单的 Standard 条目按规范域名、Listing 摘要和已知状态一致，且两份响应都明确标记 `listing_type=Standard` 时才保存正向报告。两份分页有各自完整性检查。未识别的类别或状态、跨读取变化与第二次读取失败保留显式未知。此读路径不产生下架已完成、所有权已验证或可调写入的结论。
匿名 Standard 筛选实测仍返回库存路由已知的凭据要求，状态为 HTTP 200、`text/html`。匿名 `domain-details` 同样返回 HTTP 200、`text/html`，实际 JSON 为 `{"message":"Invalid API token or insufficient permissions"}`。该响应只表示认证或权限失败。授权账号内精确缺席的结果仍需取证。

已接入的 Standard 下架使用同账户的 `domain-details` 复核正向挂牌，要求精确域名、同一 Listing 摘要、明确 Standard 和已观察的 `Seller Approved`。Native 只接受官方 `Successfully removed the domain` 作为请求回执。重开只读 `domain-details`，挂牌仍在或无法确认的结果均保留未核实。通用 404、空数组、null、筛选缺席和匿名错误无法证明账户内缺席。[官方详情](https://apidocs.atom.com/api-reference/seller_apis/domain_details) [官方下架](https://apidocs.atom.com/api-reference/seller_apis/remove_domain)

2026-11-24 重读官方 OpenAPI 1.0.0 的 [add-domain](https://apidocs.atom.com/api-reference/seller_apis/add_domain)：`GET https://www.atom.com/api/marketplace/add-domain`，查询参数 `api_token`、整数 `user_id`、`domain_type`（standard | premium | geo，可选且未写默认）、`domain_name`、`price`（字符串，未写币种或上限）。200 响应示例为 `{"message":"Successfully uploaded"}`，schema 示例为 “Successfully updated”；未记录错误响应与幂等性。Native 已组合 Standard 上架发送：显式发送 `domain_type=standard`，价格为 1–49,999,999 的整数美元字符串，只接受上述两条文档回执，且回执不代表挂牌存在。同日 [domain-details](https://apidocs.atom.com/api-reference/seller_apis/domain_details) 仍返回 `selling_price`、`full_price`、`listing_type`（示例 “Plus”）；Native 只把精确整数的 `selling_price` 作为写后价格比对值。**币种按 USD 实施仍待真实账号核对**：受控上架后 `selling_price` 必须等于提交的整数美元，否则该项为冲突，能力不得取得资格。

`verify-dns` 只返回 `DNS check request accepted`。详情示例的 `status: Seller Approved` 是 Listing 状态示例，
文档未证明它可替代 DNS/owner 验证终态；需核实 challenge 获取和可观测终态，不能据此宣称验证闭环完成。

当前 Atom 帮助中心将 Standard、Plus 和 Premium 分别列为挂牌类型。因此使用 `type=standard` 作正向核对时，`Plus` 或 `Premium` 不能提升为 Standard。Standard 的 TXT 路径从卖家账户 My Domains 的「Verify now」获取 Verification Code，同一个代码可用于该账户的多个域名。公开说明仍含旧 Squadhelp 品牌，具体 TXT 名称、当前账号 challenge 的响应合同及平台终态需从真实受控会话取证。此处不采用文章中的站点指向步骤作为验证写入依据。[挂牌类型](https://www.atom.com/help/article/what-are-standard-plus-and-premium-listings) [所有权验证](https://www.atom.com/help/article/how-to-verify-your-standard-premium-domains)

### SellerHub 与 Sedo

- SellerHub 的官方 OpenAPI 1.0.0 定义固定来源 `https://spaceship.dev/api`。无筛选的 `GET /v1/sellerhub/domains` 需要 `sellerhub:read`，返回 `items` 与 `total`，按 `take/skip` 分页。Listing 由域名寻址，列表不返回独立不可变 ID。报价为 USD 十进制字符串，启用标志分别返回。Linux 对该入口的匿名 HTTPS 请求返回 401 和 `application/problem+json`；认证列表合同与账号内结果仍待实测。[官方合同](https://docs.spaceship.dev/#tag/SellerHub)
- SellerHub 官方说明创建记录后等待 DNS 传播，系统自动验证；列表状态包含 `verifying`、`onSale`、
  `onSaleStopped`、`saleProcessing`、`failed` 等。以账户内目标 Listing 的新鲜读取确认结果。
- 固定价上架采用官方 `POST /v1/sellerhub/domains`。Native 在认证库存中确认目标缺席后，仅提交规范域名、USD 一口价和关闭议价的条款。201 作为回执。精确 GET 必须返回同域名、`onSale` 和批准的完整条款，才确认在售。`verifying` 保留为等待所有权验证。已实现官方验证记录的 TXT 选项解析，适用选项内的全部记录共同构成一个验证条件。认证创建、待验证与在售读回仍待实测。
- 一口价变更采用官方 `PATCH /v1/sellerhub/domains/{domain}`，需要 `sellerhub:write`。当前客户流程只提交 `binPrice.amount`，允许的输入以整数美分保存。精确 GET 必须返回同域名、在售且启用一口价，读回批准目标价才确认成功。HTTP 200 是发送回执，通用 404 保留未知。当前验收未取得获准卖家账户的认证响应。
- 匿名读取精确域名与验证记录路径均返回 401 和 `application/problem+json`。公开合同列出精确 GET 的 404，但只规定 problem 的 `detail` 和通用错误码格式。后续下架对账仍需用获准账户区分目标缺席和其他 404，DELETE 204 作为操作回执保存。
- Sedo 官方 `DomainListExtended` 接受 XML GET 或 POST，按 `startfrom` 偏移、`results` 上限和 `orderby=0` 的域名顺序读取。Native 使用固定 HTTPS POST，认证字段只放请求体。Linux 匿名 POST 返回 HTTP 200、`text/xml;charset=UTF-8` 和结构化 `SEDOFAULT` E1（用户名为空），证明匿名请求到达该端点。源码只接受完整校验的空 `SEDODOMAINLIST` 作为终页。通用 E15 缺少账户列表的终页证据，仍按故障处理。认证正向分页、空账户和全量边界待实测。 [官方合同](https://api.sedo.com/apidocs/v1/Basic/functions/sedoapi_DomainListExtended.html)
- Sedo `DomainStatus.domainstatus` 只区分“不在 Sedo 数据库 / 在 Sedo 数据库”，`forsale` 只表示在售。
  它的参数表不要求用户名；不能单独作为账户归属或 owner 验证成功的证据。账户归属对账至少结合
  `DomainListExtended`，仍需另行取得所有权验证终态证据。

## 后续落地顺序与验收

以下是当前已识别的私有 API 开发清单，按既定市场优先级推进。列入开发不表示端点合同已取得或能力已实现。
每项由对应平台 `secure-host-core` 私有 Service 实现，跨平台 DNS 与续作由本地 operations 编排。

| 平台 | 直接进入私有 API 开发的缺口 | 保留的官方路径 |
| --- | --- | --- |
| Afternic | 所有权验证记录获取、冲突验证触发，以及与官方状态读取衔接。 | Listing 读写、批量任务、状态查询及已公开的重提接口。 |
| Atom | 验证要求获取、验证终态读取的未公开部分；账号不具备官方 API 准入时的正常卖家操作适配。 | 已公开且账号获准的 Seller API，包括 DNS 检查触发。 |
| Sedo | 所有权 challenge 获取、验证触发及账户验证结果读取的未公开部分。 | Listing 读写和账户域名列表；DomainStatus 仅按其实际语义使用。 |
| 易名 | 账户资产读取、批量上架/下架、所有权验证及结果对账的当前缺口。 | 当前没有已取得具体合同的上述官方卖家能力。 |
| 阿里云 | 卖家上架/下架、所有权验证及卖家状态读取的当前缺口。 | QueryDomainList、ScrollDomainList 等已确认资产读取接口。 |
| 22.cn | 账户资产读取、批量上架/下架、所有权验证及结果对账的当前缺口。 | 代理 API 的存在只作事实记录，未取得合同的能力不假定已受官方支持。 |

SellerHub 当前已核实的 Listing 与验证记录继续走官方 API。其他能力核查若发现未获官方支持的缺口，
同样纳入对应平台私有 API 工作包，不再另设官方/社区/私有的路线选择待决项。

1. Afternic、Atom、SellerHub、Sedo 的已公开 Listing 读写按官方合同实现；市场优先级保持产品既定顺序。
   SellerHub 验证流程可用来验证跨平台 DNS 编排，但不能把它的 wire 格式作为其他平台事实。
2. 当前缺口按上表直接进入自研私有 API 工作包，包含协议调查、实现及验证；社区线索供参考，
   不再等待社区实现或更多官方资料。已确认的官方能力继续原路径，不整体切换平台。
3. 每项调查需记录具体 endpoint/method、来源、账号权限、认证/CSRF、分页/限流、请求字段、响应与副作用。
   尚无账号会话与受控域名证据的私有接口，先执行开发工作包中的协议验证步骤；本轮决策不代表实现完成。
4. 每个平台一个 `secure-host-core` 私有 Service。已确认官方支持的能力走官方路径，其余当前缺口走私有 HTTP 路径；
   社区代码仅供参考，实际实现由同一 Service 持有。任务记录实现版本、资源和批准范围，超时进入未知结果对账，不自动换另一条写入路径。
5. 对每项能力验证读取 → 批量预览 → 单次确认 → 逐项写入 → 等待验证 → 新鲜对账；覆盖部分失败、
   会话过期、验证码/MFA、价格单位、交易锁定、进程中断与重开续作。新增扣款或扩大 DNS/权限修改时重新确认。
6. 私有 Cookie/CSRF/Token 仍属 Native 本地秘密；不能提交给社区托管代理。Windows/macOS 分别验证
   凭据输入、保管与失效恢复。文档修改不启用任何未经实现及资格化的 Provider 执行能力。
